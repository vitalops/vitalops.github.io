Open-source tools for running LLMs in production.

vitalops plan works out whether a model fits on a GPU, how fast it will run, how many GPUs it needs and what it will cost. vitalops bench measures a running server and compares it with the plan. No dependencies; Python 3.9 or newer.

pip
pip install vitalops
vitalops plan Qwen/Qwen3-32B --gpu h100 --users 64
vitalops bench http://localhost:8000 --plan h100
one file, no install
wget https://github.com/vitalops/vitalops/releases/download/onefile/vitalops.py
python vitalops.py plan qwen3-32b

The planner, interactive

Every figure in this panel comes from vitalops's Python source, loaded into Pyodide (about 7 MB on the first visit). The command that prints the same report is under "Command line". Any public Hugging Face model can be loaded from the model list. vitalops ui serves the same panel from the installed package.

First-order estimates from public specifications, not measurements. Every formula is under "How this is calculated" in the panel.

What it models

For a batch of b requests on a tensor-parallel group of tp GPUs.

Memory

Weights are parameters × bytes per parameter (bf16 2, fp8 1, int4 0.5625 with group scales), split across the group. The KV cache is 2 × layers × KV heads × head dim × bytes per value per token, or the latent width for models with latent attention; each request reserves prompt + output tokens. 8% of memory plus 1.5 GB is kept for the runtime.

Time

A decode step is max(memory time, compute time) + all-reduce time: the weights (the experts a batch touches, for a mixture of experts) and the batch's KV cache at 75% of peak bandwidth, against 2 × active parameters × b at 50% of the dense tensor-core rate. Prefill runs at 60% of that rate and is amortised over the batch's output tokens.

Layout and cost

Tensor parallelism costs two all-reduces per layer over the GPU's link, with 8 µs latency on NVLink or Infinity Fabric and 25 µs on PCIe. For each degree 1, 2, 4, 8 that fits, the KV cache sets the batch per replica and so the replica count; the fewest GPUs that meet the TTFT target win. Cost is GPUs × price per hour ÷ output tokens per hour.

Not modelled: queueing, speculative decoding, prefix caching, chunked prefill, kernel efficiency at small batches, pipeline or expert parallelism. The physics page has every formula.

Measure it, next to the plan

vitalops bench sends concurrent streaming requests to any OpenAI-compatible server (vLLM, SGLang, TGI, llama.cpp, a hosted API) and reports what users see at each concurrency level. With --plan, the planner's estimate for the same traffic sits under each measured row, and large gaps are named.

$ vitalops bench http://localhost:8000 --users 1,8,32,64 --prompt 1024 --output 256 --slo 500 --plan h100 --tp 1
$ vitalops bench $ENDPOINT --users 32 --slo 400 --require 32 -q || exit 1     # in CI

What it reports

Per concurrency level: time to first token and time between tokens at p50 and p95, tokens per second per stream and in total, requests per second, and failed requests. The capacity line is the most concurrent requests whose p95 TTFT meets the target.

How it measures

A closed loop per level, one keep-alive connection per worker, with the first request of each worker discarded as a warm-up. Prompts are random words calibrated to the server's own token counts, distinct per request unless --shared-prefix asks for a common system prompt. Outputs are held to the asked length where the server allows it, and the report says when it does not.

Against the plan

The plan is one replica on the GPU you name, at the measured concurrency. When TTFT runs far above it, requests are queueing behind other prefills; when a single stream runs far below it, small-batch overheads; when TTFT runs below it with a shared prefix, the prefix cache. The bench docs cover the rest.
