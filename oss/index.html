Commands

One command for each step of running a model

Size the deployment before you rent anything, check the server once it runs, and check that a cheaper format still gives the same answers. Each command works on its own, and they share one catalogue of models and GPUs.

vitalops plan

Will it fit, how fast will it run, and what will it cost

Give it a model and a GPU. It reads the model's shapes from the Hugging Face Hub, takes the GPU from a catalogue of datasheet figures, and finds the fewest GPUs that meet your time-to-first-token target.

  • Any repository id works, including mixtures of experts and latent attention; gated models read with HF_TOKEN.
  • Tries tensor parallelism 1, 2, 4 and 8 over the GPU's real link, and as many replicas as the KV cache needs.
  • --all-gpus compares the whole catalogue at once, priced per million output tokens.
  • Prints every assumption, and exits 1 when the model doesn't fit, so a script can check it.

Weights read

Decode is memory-bound: every step reads the weights, or for a mixture of experts the experts the batch touches.

weight bytes ÷ (bandwidth × 0.75)
KV cache read

Each running request's cache is read every step, so it grows with the batch and the context.

batch × context × KV bytes ÷ (bandwidth × 0.75)
All-reduces

Tensor parallelism adds two all-reduces per layer over the GPU's link. Cheap on NVLink, expensive on PCIe.

2 × layers × (bytes ÷ link + latency)
Prefill share

Prompts are processed between decode steps, so long prompts slow every stream down.

batch × prefill time ÷ output tokens

Not in the estimate: queueing, prefix caching, speculative decoding, chunked prefill and real kernel efficiency at small batches. vitalops bench measures what those do on your server. Every formula.

vitalops bench

Measure the server, at the load you will run it at

Point it at any OpenAI-compatible endpoint: vLLM, SGLang, TGI, llama.cpp or a hosted API. It runs each concurrency level as a closed loop of streaming requests and reports what users would see.

  • Time to first token and time between tokens at p50 and p95, tokens per second per stream and in total.
  • Prompts are sized with the server's own token counts and differ per request, unless --shared-prefix asks for a common system prompt.
  • --plan h100 prints the estimate under each measured row and names the likely cause of a large gap.
  • --require 32 exits 1 when the target is missed at 32 users, to stop a deploy in CI.
How it measures
waiting and prefilla streamed tokenwarm-up, not countedmeasured request
TTFT far above the planQueueing

Requests wait behind other prompts' prefill. The plan's TTFT is one prompt on an idle replica, so this gap grows with concurrency.

one stream far below the planSmall-batch overheads

At one request, kernel launches and scheduling cost more than the memory reads the plan counts.

TTFT below the plan, shared prefixPrefix cache

The shared part of the prompt is served from cache instead of being prefilled again, which the plan does not model.

Install

Python 3.9 or newer, nothing else

No compiled extensions and no dependencies, so it installs anywhere Python runs: a laptop, a CI runner or the GPU box itself.

pip

The vitalops command and the Python package.

pip install vitalops
vitalops plan qwen3-32b --gpu h100

One file

The whole package in a single script, the planner page included.

wget https://github.com/vitalops/vitalops/releases/download/onefile/vitalops.py
python vitalops.py plan qwen3-32b
